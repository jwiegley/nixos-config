## What this document is

A complete, implementation-ready gap analysis of monitoring coverage for **every
subsystem** of vulcan, produced by a 17-domain read-only census of the **live system**
(`/api/v1/...` against Prometheus, `systemctl`, `ss`, `podman`, `zfs`, `psql`, endpoint
`/metrics`) cross-referenced with the NixOS config in `/etc/nixos`. Each subsystem was
evaluated across four dimensions — **soundness** (is it up?), **correctness** (is it doing
the right thing?), **security**, **performance** — and every gap carries a concrete
recommendation, whether a backing metric already exists, a severity (P0/P1/P2), and effort.

**Scope censused:** 126 running services · 85 timers · 16 rootless-container users (19
containers) · 2 microVMs · 26 PostgreSQL DBs · 8 Redis instances · 58 ZFS datasets ·
69 blackbox probe targets · 37 Prometheus scrape jobs · 35 alert files · Nagios (active)
· Loki ruler · Node-RED (HA safety) · VictoriaMetrics (HA push).

**Result:** **203 coverage gaps** — **15 P0**, **83 P1**, **105 P2**.
By dimension: **correctness 79**, soundness 56, performance 35, security 33.

> **Headline:** the system is *strong* on soundness/availability (blackbox reachability,
> systemd unit-state — now that the dead-metric defect is fixed — and certificate
> lifecycle) but *weak on correctness* (silent failures: a job exits 0 but produced
> garbage/nothing) and on **host-level security** (SSH/auth/intrusion). The single most
> important structural gap is that **there is no dead-man's switch** — if the whole
> alerting pipeline dies, nothing tells you.

## For the implementer (Fable): conventions & guardrails

**Where things live / how to add them** (all under `/etc/nixos`):
- **Alert rules**: `modules/monitoring/alerts/*.yaml` — auto-discovered by
  `modules/monitoring/services/alerting.nix`; just add a file or a rule. `promtool`
  validates ALL rule files at build time (`services.prometheus.checkConfig`), so a bad
  expr fails the build.
- **Loki/log rules**: `modules/monitoring/loki-rules/*.yaml` (LogQL, against `job="systemd-journal"`).
- **Scrape jobs**: any module may set `services.prometheus.scrapeConfigs = [ {...} ]`; the
  list **merges** across modules. Self-monitoring jobs were just added in
  `modules/monitoring/services/self-scrape.nix` — follow that pattern.
- **Exporters**: `modules/monitoring/services/*.nix` (e.g. `redis-exporter.nix`,
  `health-check-exporters.nix`). The **textfile-collector pattern** (write
  `*.prom` to `/var/lib/prometheus-node-exporter-textfiles/`, picked up by `job=node`) is
  the established idiom for "did this oneshot succeed / when / how big" metrics — see
  `container-health-exporter.nix` and `backups.nix`.
- **Blackbox**: `modules/services/blackbox-monitoring.nix` (modules + target lists).
- **Build/switch**: `sudo nixos-rebuild build --flake '.#vulcan' --cores 0` then `switch`.
  Create `/etc/nixos/.nixos-build` as a lock before building and remove it after (wait if
  it exists — another session may be building). `--cores 0` matters on this throttled aarch64 box.

**PromQL conventions on this host (learned the hard way today):**
- node-exporter systemd metric is **`node_systemd_unit_state`** (NOT `systemd_unit_state`).
  Its `type` label is the systemd **`Type=`** directive (`simple`/`oneshot`/`notify`/...),
  **not** the unit kind — filter unit kind with `name=~".*\\.service"` (regex dot = **`\\.`**,
  double-backslash, in both plain `expr:` and `expr: |` block scalars).
- It is a **continuous state-set** metric: the `state="failed"` series exists at value 0
  normally, so a bare selector with no comparison fires constantly — always add `== 1` / `== 0`.
- **node-exporter only sees SYSTEM units**, not rootless `systemd --user` containers
  (`home-manager-*.service` is just the activation oneshot, inactive by design). Monitor
  rootless-container apps via **blackbox HTTP probe** or the **container-health-exporter**.

**Security (MANDATORY — this repo has strict secret rules):** never read/echo `/run/secrets/*`,
`/etc/NetworkManager/system-connections/*`, `*.age`, `secrets.yaml`, hass `.storage/*`, any
`*.env`/`settings.json` with keys; never `sops -d`; never dump full `/metrics`/configs/journal
that may carry tokens/PII/IPs beyond `docs/ports.txt`. New exporters that open a listening port
**must be added to `docs/ports.txt`**.

**Validate every recovery** the way today's work did: after switch, query the new metric/rule
against live Prometheus (`/api/v1/query`, `/api/v1/rules` → `health=ok`), and confirm no rule
fires spuriously (`rate > 0` on a metric with a nonzero baseline will chronically alarm — pick
thresholds against the *observed* baseline, e.g. the `VictoriaMetricsSlowInserts` `>0`→`>10/s` fix).

## ⚠️ Two live findings discovered & acted on during this analysis

1. **redis-litellm is NOT down — the exporter address is wrong.** `redis-exporter.nix` points
   `-redis.addr` at `redis://10.88.0.1:8085`, but the litellm Redis binds **`127.0.0.1:8085`**
   (verified: `127.0.0.1:8085` → `PONG`; `10.88.0.1:8085` → connection refused). So
   `redis_up{job="redis"}=0` and `redis_exporter_last_scrape_error=1` **permanently**, with no
   alert. This corrects an earlier mis-report ("litellm redis is down"). **Fix:** change the
   address to `127.0.0.1:8085` (P0, redis domain). *Not yet applied.*

2. **`asymmetric-routing` rules silently dropped after boot — restored at runtime.** The pri
   50/51 source-policy ip rules (cross-subnet routing from `192.168.1.2`) were **absent from the
   kernel** during this analysis, even though the fail-loud oneshot reported `Result=success`
   (it last ran at the 13:21 deploy and verified them present *then*; they dropped later with no
   re-detection). I re-ran the oneshot to restore them (count back to 2). **This proves the
   run-time verify is insufficient — needs a continuous textfile gauge** (P0, networking domain).

## Cross-cutting / systemic patterns (apply these broadly — they generate most of the 83 P1s)

1. **"Scraped but unalerted" is the dominant pattern.** Many domains expose rich, *live* metrics
   with **zero alert rules** (host thermals/fans/time-sync; litellm; opnsense; openproject
   Rails/Puma; HA-pushed pool sensors in VictoriaMetrics; etc.). Most P1s are **rule-only**
   additions on metrics that already exist — cheap, high-value. Sweep each domain's Part B
   `backingMetricExists: ✅` rows first.

2. **Correctness needs the "last-success" triad.** For *every* oneshot/timer that produces an
   artifact (backups, syncs, cross-checks, cert renewals, flume backfill, snapshots), emit a
   textfile triad: `<job>_last_success{}` (1/0), `<job>_last_timestamp_seconds`, and a
   size/row-count where applicable — then alert on **stale** (didn't run) + **failed** +
   **size-regression** (produced garbage). A green systemd exit is NOT correctness. This single
   pattern closes ~15 correctness gaps.

3. **A host-wide `TargetDown` catch-all (`up == 0 for: 5m`)** backstops every current and future
   scrape job in one rule — add it once.

4. **Freshness/staleness on pushed metrics.** HA→VictoriaMetrics is push-based; if it stalls,
   rules reading those series go quietly stale (not "firing", just frozen). Add an
   `absent_over_time()` / max-timestamp staleness alert per push source.

5. **Security is the thinnest pillar.** Beyond cert lifecycle (well-covered), there is little:
   no SSH/auth alerting, no sudo-anomaly, no fail2ban surfacing, no listener-drift vs
   `docs/ports.txt`, no package/CVE-age signal. Treat security as a deliberate workstream
   (P0 #13 is the entry point; the security domain in Part B lists the rest).

6. **Decide the monitoring topology (Prometheus vs Nagios vs Node-RED).** **[RESOLVED
   2026-08-19 — do not action this item.]** The topology was settled by deletion rather than
   by integration: Nagios was removed entirely, leaving Prometheus + Alertmanager as the only
   alerting system, with Node-RED scoped to Home Assistant safety automations. There is
   nothing left to bridge. *Original text:* three overlapping alerting systems exist; the
   deleted Nagios rules expose that Nagios results aren't surfaced in Alertmanager; either
   bridge Nagios→Alertmanager (one integration) or formally scope each layer's responsibility
   — and **document it** so future "dead rule" placeholders don't recur.

7. **Notification path must itself be monitored** (P0 #5) — and the dead-man's switch (P0 #4)
   must terminate at an **external** endpoint, or a total-host failure is unobservable.

## Host & Hardware  `[host-hardware]`

**Gaps:** 10  (P0:2, P1:4, P2:4)  |  **Components:** 11


vulcan's host-hardware monitoring is strong on the classic capacity dimensions (disk space, RAM, zram/disk swap, CPU utilization — all in system.yaml on real, populated node-exporter metrics, with a thoughtfully zram-tuned thrash detector) and node-exporter soundness is implicitly covered by up{job=node} + systemd unit-state alerts. The biggest risks are concentrated in the disk/USB-bridge subsystem and in thermal/time correctness, all of which are scraped-but-unalerted or not scraped at all. P0 gaps: (1) the OWC UAS enclosure (1e91:a4a7) hang is only caught AFTER tank drops via the downstream ZFS-pool-missing cascade — there is NO early-warning Loki rule on the kernel uas_eh_abort/ESHUTDOWN/USB-reset signatures even though promtail already ingests kernel journal lines (rule-only fix); and (2) SMART is entirely absent (smartd inactive, no exporter), so the 4 single-mirror-leg 14.6T UAS disks and the NVMe root have zero proactive failure/UDMA-CRC/temperature visibility — UDMA_CRC_Error_Count is specifically the leading indicator that the very enclosure that hangs is degrading. P2: metric-based OOM (node_vmstat_oom_kill), load-average saturation (good D-state/IO-stall proxy), file-descriptor/inode exhaustion, and hwmon hardware-alarm bit. Of the 20 deleted rules, only ZFSSnapshotAgeTooOld falls in this domain; its intent is valid and should be RESTORED on the real metric zfs_replication_last_run_timestamp_seconds rather than the non-existent node_zfs_snapshot_timestamp it originally referenced. Net: ~10 low-effort rule additions plus one med-effort smartctl_exporter would close essentially every gap, and almost all backing metrics already exist (the exceptions are SMART and the kernel-log UAS rule).

The external-deps-correctness domain is the host's biggest silent-failure blind spot. Soundness is reasonably covered (blackbox probes + scrape jobs + node_systemd for the native services; trader/litellm endpoints are watched), but CORRECTNESS - the actual point of this domain - is largely unmonitored.
