2026-08-14 -- backtrace analysis. All twenty crashes are ONE bug, not twenty.

Extracted the first eight frames from every etterminal core and compared their
low 16 bits, which are invariant under ASLR:

    20 x  2134 2120 bb1c 59c0 4e70 a318 b714 9a94
    total traces examined: 20

A single signature, 20/20. Different processes, different ASLR bases, identical
call site. That rules out random memory corruption and points at one
deterministic code path.

Shape of the stack: frames #0-#3 sit at 0x7f.../0x7e... addresses (shared
library) and frames #4-#7 at 0x55.../0x558... (the main executable). SIGABRT
raised from inside libc with application frames below it is the classic
abort()-from-library pattern; for a C++ program like Eternal Terminal the
overwhelmingly likely cause is an uncaught exception reaching std::terminate,
or a failed assertion.

FIX APPLIED -- rsync resumability (deployed and verified reaching rsync):
    --partial-dir=.rsync-partial

Without --partial, a dropped connection discards the entire in-flight file. At
the ~1 MB/s this link sustains, any file needing longer to transfer than the
mean time between drops can NEVER complete -- every run restarts it from zero.
That is a convergence failure no timeout value can fix, and it matches the
observed behaviour exactly: 424G logical in the destination, yet never a
completed pass.

--partial-dir (not bare --partial) keeps partials in a side directory, so the
destination never holds a truncated file under its real name. The path is
relative, so rsync appends its own perishable exclude and --delete will not reap
the partials before they are reused -- checked against the rsync 3.4.1 man page,
and our filter list never mentions .rsync-partial so nothing shadows that rule.
--timeout=600 bounds the other failure shape, a stalled-but-open stream, which
would otherwise sit until the 12h ceiling and waste the entire window.

verified end-to-end -- run 2 moved 0 bytes, so no partial has been created or
