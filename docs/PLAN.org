2026-08-14 -- backtrace analysis. All twenty crashes are ONE bug, not twenty.

Extracted the first eight frames from every etterminal core and compared their
low 16 bits, which are invariant under ASLR:

    20 x  2134 2120 bb1c 59c0 4e70 a318 b714 9a94
    total traces examined: 20

A single signature, 20/20. Different processes, different ASLR bases, identical
call site. That rules out random memory corruption and points at one
deterministic code path.

Shape of the stack: frames #0-#3 sit at 0x7f.../0x7e... addresses (shared
library) and frames #4-#7 at 0x55.../0x558... (the main executable). SIGABRT
raised from inside libc with application frames below it is the classic
abort()-from-library pattern; for a C++ program like Eternal Terminal the
overwhelmingly likely cause is an uncaught exception reaching std::terminate,
or a failed assertion.

BLOCKED ON SYMBOLS. The nixpkgs eternal-terminal binary is stripped -- every
frame resolves as "n/a (n/a + 0x0)" -- so the crashing function cannot be named
from these cores. Options if this is worth pursuing:
  - rebuild eternal-terminal with `separateDebugInfo = true` (or a debug
    output) via an overlay, then re-symbolize a fresh core;
  - or check upstream: a deterministic abort in a widely used client is likely
    already reported against 6.2.11.
Neither is worth doing on spec for a P4, but the single-signature finding makes
either one cheap to act on, since any single new core reproduces the same path.

Confirms the earlier read: this is a real, repeatable bug rather than
environmental flakiness. It remains client-side only -- eternal-terminal.service
(the SERVER) is still active with NRestarts=0 since 2026-07-03.

2026-08-14 -- ROOT CAUSE FOUND, without needing debug symbols. Eternal Terminal
writes its own client logs to /tmp/etterminal-$USER-*.log, and they name the
crash site directly.

Every one of the twenty cores has a matching log, and all twenty abort at the
SAME source location:

    [FATAL ... terminal-main UserTerminalHandler.cpp:107] Stack Trace:
    ...
    Error: (2): No such file or directory
    [WARNING ... UserTerminalHandler.cpp:107] Aborting application.
        Reason: Fatal log at [/build/source/src/te...]

So: ENOENT (errno 2) is turned into a glog LOG(FATAL), which calls abort()
rather than being handled. That independently confirms the earlier
backtrace-signature finding (20/20 identical low-16-bit frame offsets) by source

THIS IS THE NORMAL EXIT PATH, not a rare fault. Of 23 etterminal session logs

whenever they end. The last ordinary log line before the fatal is consistently
