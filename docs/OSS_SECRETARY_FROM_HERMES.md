# Asking Hermes about GitHub & Gitea

**What this is:** how to query your open-source triage data conversationally through
Hermes, what it can and cannot tell you, and how to tell a stale answer from a wrong
one. Added 2026-09-04 (`aa4390a9f`).

**The short version:** ask Hermes in plain language on Discord. It reads a daily
snapshot of the `open-source-secretary` database — so it knows *what* is open and who
is waiting on you, as of this morning, but never what anyone actually said.

---

## What changed, and what deliberately did not

The daily 07:00 triage email is **unchanged**. It is still generated by
`open-source-secretary`, which does its own GitHub and Gitea API calls with its own
tokens and uses Hermes only as a completion endpoint for prioritisation.

What was added is a read-only view of that work's **result**. Hermes gained six query
tools over a snapshot of the secretary's database. It did **not** gain forge access:
no GitHub or Gitea credential exists inside the Hermes VM, and the GitHub/Gitea MCP
servers removed in `3af2dabfb` for context cost stay removed.

This split is deliberate. A wrong answer to a question you asked is visible in context
and correctable in the next message. A wrong daily email arrives once, unchallenged,
and is trusted. So generation stays deterministic and only querying is conversational.

---

## Asking

Talk to Hermes as usual — Discord (`@Hermes`), or the OpenAI-compatible API on `:8080`.
There is no special syntax; the tools are simply available.

| What you want | Ask something like |
|---|---|
| Threads where someone is waiting on you | *"What's awaiting my reply?"* · *"…on ledger?"* |
| Current open work | *"What issues are open on ledger-mode?"* · *"Any open PRs?"* |
| Dropped balls | *"What's gone stale in the last 30 days?"* |
| Shape of the backlog | *"Which repos have the most open issues?"* |
| Finding something specific | *"Any open issues mentioning 'parser'?"* |
| How current the data is | *"How fresh is your OSS data?"* |

If Hermes reaches for the wrong tool, name it directly — e.g. *"use oss_stale_threads
with days=90"*.

### The tools, if you want to be precise

| Tool | Answers | Useful parameters |
|---|---|---|
| `oss_snapshot_age` | when the data was last refreshed | — |
| `oss_awaiting_reply` | open threads whose last comment was **someone else's** | `repo`, `limit` |
| `oss_open_threads` | open issues/PRs, newest activity first | `repo`, `kind` (`issue`/`pr`), `limit` |
| `oss_stale_threads` | open threads untouched for N days | `days` (default 30), `limit` |
| `oss_repo_summary` | per-repo open issue/PR counts, busiest first | `limit` |
| `oss_search_titles` | substring search over titles | `query`, `include_closed`, `limit` |

`repo` is a substring match, so *"ledger"* matches `ledger/ledger`, `ledger/ledger-mode`
and so on.

## What it cannot tell you

**No bodies.** The secretary stores issue and PR *titles*, never the text of issues or
comments. Hermes can tell you a thread exists, who commented last and when — it cannot
summarise the discussion. *"What did they say in #412?"* is out of scope by
construction, not by policy.

**Not live.** Answers are as of the last 07:00 run. If you closed something an hour
ago, Hermes still thinks it is open. Ask *"how fresh is your OSS data?"* whenever the
answer matters; that is exactly what `oss_snapshot_age` is for.

**Only the secretary's scope.** Your GitHub repos plus the `ledger` org, and `johnw`'s
Gitea repos, with mirrors filtered out. If a repo never appears in the daily email, it
is not here either.

**No writes.** Nothing here can comment, close, label or open anything. It is a
read-only view.

## Reading the answers

**"Awaiting reply" means the last comment was not yours.** It is a heuristic over
`last_commenter`, not a judgement about whether a reply is actually owed. A bot's
comment counts as someone else's.

**Large open counts are usually real.** Some repos legitimately carry hundreds of open
issues; `jwiegley/category-theory` alone accounts for ~666 of the ~1,168 open threads.
That is the repo's actual backlog, not a bug — but it does mean *"which repos have the
most open issues?"* is dominated by one repo unless you scope the question.

**A confident answer is not a fresh one.** The single most likely way to be misled here
is a correct answer to a question about a stale snapshot. Freshness is the thing to
check, not plausibility.

## If it does not work

**"I don't have a tool for that."** Check the tool is registered in the config the agent
actually reads — not the Nix store path, which is not authoritative:

```bash
sudo python3 -c "
import yaml; d=yaml.safe_load(open('/var/lib/hermes/.hermes/config.yaml'))
print(sorted(d['mcp_servers']))"
```

`oss-secretary` should be in that list. Note the key is `mcp_servers` (snake_case).
`hermes-vm.nix` documents that the upstream config merge never *deletes* keys; additions
normally land, but a missing entry here means the merge is the first suspect.

**Answers are days old.** The snapshot is written by `open-source-secretary`'s
`ExecStartPost` after each run, so a stale snapshot means the secretary itself has not
run:

```bash
systemctl status open-source-secretary
ls -l /var/lib/hermes/oss-secretary/state.db
```

Note that **nothing currently alerts if the daily run stops** — neither this service nor
`hermes-nightly-report` is covered by any alert rule. A silently missing report is the
known gap, so it is worth checking this by hand if the data looks old.

**The tool errors.** Verify the server runs standalone on the host:

```bash
sudo OSS_SECRETARY_SNAPSHOT=/var/lib/hermes/oss-secretary/state.db \
  python3 /etc/nixos/scripts/oss-secretary-mcp.py --selftest
```

That prints snapshot age and a few counts without needing an MCP client.

## How it works

```
open-source-secretary (host, 07:00 daily)
  ├── GitHub + Gitea APIs, own SOPS tokens ──> deterministic digest ──> email
  └── ExecStartPost: sqlite3 .backup ──> /var/lib/hermes/oss-secretary/state.db
                                              │  (already the read-write state share)
Hermes microVM ── oss-secretary MCP ──────────┘  six parameterised queries, mode=ro
```

Three design choices worth knowing if you ever change this:

- **A snapshot, not the live database.** A guest reading the live file across virtiofs
  while the host writes it can see a torn read; `sqlite3 .backup` is SQLite's online
  backup API and is safe against concurrent writes. It also lands in `/var/lib/hermes`,
  which is *already* shared, so no `microvm.shares` change was needed.
- **Fixed parameterised queries, never free-form SQL.** A model that can compose
  arbitrary SQL can read every column, which defeats the point of curating the view.
  `http_cache` and `meta` are not exposed at all.
- **`ExecStartPost` is prefixed `-+`.** `+` runs it as root (the service user cannot
  write `hermes:hermes 0750`, and it also lifts `ProtectSystem=strict`); `-` makes a
  snapshot failure non-fatal, because the email is the product and this is a convenience
  view of it. It is *not* `|| true` — systemd `Exec` lines are not a shell and would
  pass that as two literal arguments.

**Files:** `scripts/oss-secretary-mcp.py`, the `ExecStartPost` in
`modules/services/open-source-secretary.nix`, and the `oss-secretary` entry in
`modules/services/hermes-vm.nix`.
