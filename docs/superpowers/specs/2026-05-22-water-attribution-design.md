# Water Attribution Tracking — Design

Status: **Draft** · Date: 2026-05-22 · Author: John Wiegley (via Claude)

Track and attribute every gallon Flume measures into distinct categories — pool
auto-fill, per-zone irrigation, hot-water domestic use, and residual "other" —
with daily / weekly / monthly totals visible in Home Assistant and Grafana,
weekly email reports, and a historical backfill that reconstructs months of
prior data from VictoriaMetrics and the Flume API.

Three phases, deployed as one feature:

* **Phase 1** — Live attribution, expressed entirely as declarative Home
  Assistant entities (template, history_stats, statistics, integration,
  utility_meter). No Node-RED, no external state machine. A Nix module
  generates the package YAML from a single typed configuration.
* **Phase 2** — Weekly Python systemd unit that cross-checks HA's tally against
  the Flume Personal API and against VictoriaMetrics, and emails a human-friendly
  water report with anomaly section.
* **Phase 3** — Multi-source historical backfill that reconstructs the same
  categories as far back as data exists in VictoriaMetrics or the Flume API,
  writing the result to VictoriaMetrics + HA Long-Term Statistics + CSV.

## Why HA, not Node-RED

The detection and integration logic could live in Node-RED, but the user
explicitly chose to keep all data-gathering and per-category counting inside
Home Assistant. Node-RED stays available for *consumer* automations later
(alerts, Discord messages, threshold triggers) — none of those are part of this
spec.

## Scope

In scope:

* Live per-minute attribution of `sensor.flume_sensor_sierra_oaks_current`
  into the four categories
* Per-zone irrigation gating using `valve.sprinkler_control_*_zone` open/close
* Hot-water domestic category from NaviLink Lite
  (`sensor.water_heater_ch1_ch1_unit1_hot_water_flow`)
* Daily / weekly / monthly totals per category via `utility_meter`
* Generation of the package YAML from a Nix module so the zone list and
  detection thresholds live in one declarative place
* Weekly water report email (always) + cross-check anomaly section (when
  divergence exceeds tolerance)
* Multi-source backfill writing to VictoriaMetrics, HA LTS, and CSV

Out of scope (deferred):

* Node-RED consumer automations (alerts, notifications)
* Cold-water-only indoor flow sensor — none currently installed
* Per-zone water cost (dollars) modelling
* Mobile push notifications

## Categories

Four top-level water-attribution categories:

1. **`pool_autofill`** — detected by pattern: GPM in [3.0, 5.0] for ≥9 of the
   last 10 minutes, with rolling 10-min mean also in [3.0, 5.0]. Independent
   of any other signal (the user-chosen overlap policy is "both counters tick
   independently").
2. **`irrigation_<zone>`** (per-zone) and **`irrigation_total`** (aggregate)
   — gated by `valve.sprinkler_control_<slug>_zone` being `open`. Flume's
   instantaneous GPM is attributed to the open zone for each minute the
   zone is open. Per-zone counter is monotonic; aggregate is a sum-template
   with drop tolerance to absorb transient dips (see §5.3).
3. **`domestic_hot`** — directly measured by NaviLink. Captures hot-water flow
   only; cold-only indoor flow (toilets, cold taps, washing-machine cold
   cycles, ice maker) is NOT captured by NaviLink and falls into `other`.
4. **`other`** — residual: Flume total minus the sum of the three above,
   floored at 0 to absorb measurement noise. Encompasses cold-water indoor +
   outdoor non-irrigation/non-pool (hose use, outdoor faucets, drip-line
   leaks downstream of B-Hyve valves).

A side effect of the residual model: `domestic_hot + pool_autofill +
irrigation_total + other == flume_total` always holds (modulo polling-jitter
in the sub-second range).

## Detection logic

### Pool autofill (pattern-based)

Three composed HA primitives:

```yaml
# 1. Instantaneous range check
template:
  - binary_sensor:
      - name: "Flume GPM in Autofill Range"
        unique_id: flume_gpm_in_autofill_range
        state: >
          {% set gpm = states('sensor.flume_sensor_sierra_oaks_current') | float(-1) %}
          {{ 3.0 <= gpm <= 5.0 }}
        availability: >
          {{ states('sensor.flume_sensor_sierra_oaks_current')
             not in ['unknown','unavailable'] }}

# 2. Blip-tolerant duration counter (history_stats)
sensor:
  - platform: history_stats
    name: "Flume Minutes in Autofill Range 10m"
    entity_id: binary_sensor.flume_gpm_in_autofill_range
    state: "on"
    type: time
    duration: { minutes: 10 }
    end: "{{ now() }}"

# 3. Rolling mean guard against high-side blips
  - platform: statistics
    name: "Flume GPM 10m Mean"
    entity_id: sensor.flume_sensor_sierra_oaks_current
    state_characteristic: mean
    max_age: { minutes: 10 }
    sampling_size: 50

# Combined activation
template:
  - binary_sensor:
      - name: "Pool Autofill Active"
        unique_id: pool_autofill_active
        state: >
          {% set mins = (states('sensor.flume_minutes_in_autofill_range_10m') | float(0)) * 60 %}
          {% set m = states('sensor.flume_gpm_10m_mean') | float(-1) %}
          {{ mins >= 9 and 3.0 <= m <= 5.0 }}
        delay_off: { minutes: 1 }
```

Semantic mapping to the user-chosen rule ("10+ min run with up to 1-min blip
tolerance, mean ∈ [3.0, 5.0]"):

* `mins_in_range >= 9` — at most 1 of last 10 minutes outside [3,5]
* `3.0 <= mean <= 5.0` — guards against upward blips (e.g., hose burst during
  autofill would push mean above 5)
* 10-minute rolling window enforces the "10+ minute" duration naturally
* `delay_off: 1 min` debounces brief float-valve cycling at the upper edge

### Irrigation per-zone (signal-based)

One identical block per zone, generated from the Nix `zones` list:

```yaml
template:
  - sensor:
      - name: "Water Front Yard Gated GPM"
        unique_id: water_front_yard_gpm_gated
        unit_of_measurement: "gal/m"
        state: >
          {% if is_state('valve.sprinkler_control_front_yard_zone', 'open') %}
            {{ states('sensor.flume_sensor_sierra_oaks_current') | float(0) }}
          {% else %}
            0
          {% endif %}
        availability: >
          {{ states('valve.sprinkler_control_front_yard_zone')
             not in ['unknown','unavailable']
             and states('sensor.flume_sensor_sierra_oaks_current')
             not in ['unknown','unavailable'] }}
        attributes:
          water_category: irrigation
          zone_slug: front_yard
          zone_type: spray
          generation: water_attribution_v1

sensor:
  - platform: integration
    name: "Water Front Yard Total"
    unique_id: water_front_yard_total
    source: sensor.water_front_yard_gpm_gated
    method: left
    unit_time: min
    unit_prefix: ""
    round: 3
```

`method: left` is mandatory; the default `trapezoidal` would over-attribute
during transitions between zones.

### Domestic hot (direct)

```yaml
template:
  - sensor:
      - name: "Water Domestic Hot GPM"
        unique_id: water_domestic_hot_gpm
        unit_of_measurement: "gal/m"
        state: >
          {{ states('sensor.water_heater_ch1_ch1_unit1_hot_water_flow') | float(0) }}
        attributes:
          water_category: domestic_hot
          generation: water_attribution_v1
```

### Residual ("other")

```yaml
template:
  - sensor:
      - name: "Water Other GPM"
        unique_id: water_other_gpm
        unit_of_measurement: "gal/m"
        state: >
          {% set total = states('sensor.flume_sensor_sierra_oaks_current') | float(0) %}
          {% set autofill = states('sensor.water_pool_autofill_gpm_gated') | float(0) %}
          {% set hot = states('sensor.water_domestic_hot_gpm') | float(0) %}
          {% set zones = [ {{ generated_zone_gated_list }} ] %}
          {% set irrigation = zones | map('states') | map('float', 0) | sum %}
          {% set residual = total - autofill - hot - irrigation %}
          {{ [residual, 0] | max | round(3) }}
        attributes:
          water_category: other
          generation: water_attribution_v1
```

## Single-source-of-truth Nix module (`§2.5`)

All zone names, detection thresholds, utility_meter cycles, and the NaviLink
sensor reference are declared in one Nix attrset. The module generates
`/var/lib/hass/packages/water_attribution.yaml` at activation time. Editing
zones = editing one Nix list and running `nixos-rebuild switch`.

### Module surface

```nix
services.home-assistant-water-attribution = {
  enable = true;
  flumeCurrentSensor = "sensor.flume_sensor_sierra_oaks_current";

  # null disables the domestic_hot category entirely
  domesticHotFlowSensor = "sensor.water_heater_ch1_ch1_unit1_hot_water_flow";

  autofill = {
    gpmMin = 3.0;
    gpmMax = 5.0;
    windowMinutes = 10;
    minMinutesInRange = 9;
    enforceMeanCheck = true;
  };

  cycles = [ "daily" "weekly" "monthly" ];
  weekStart = "monday";
  aggregateDropToleranceGal = 5.0;

  zones = [
    { slug = "front_yard";                       name = "Front Yard";                       type = "spray"; }
    { slug = "side_yard_right";                  name = "Side Yard (right)";                type = "spray"; }
    { slug = "back_wall";                        name = "Back Wall";                        type = "spray"; }
    { slug = "around_dining_set";                name = "Around Dining Set";                type = "spray"; }
    { slug = "along_driveway";                   name = "Along Driveway";                   type = "spray"; }
    { slug = "back_of_house_and_side_yard_left"; name = "Back of House and Side Yard (left)"; type = "spray"; }
    { slug = "drip_front_left";                  name = "Drip Front Left";                  type = "drip"; }
    { slug = "drip_front_right";                 name = "Drip Front Right";                 type = "drip"; }
    { slug = "planter_box";                      name = "Planter Box";                      type = "drip"; }
    { slug = "zone_5";                           name = "Zone 5";                           type = null; }
  ];
};
```

### What the module produces

1. `/var/lib/hass/packages/water_attribution.yaml` — generated by
   `pkgs.writeText`, owner `hass:hass` mode 0644, symlinked from the Nix store
2. `/etc/nixos/scripts/flume-autofill/zones.json` — same canonical list in
   JSON, consumed by Phases 2 and 3 (zero duplication)
3. A `systemd.services.home-assistant.restartTriggers` hook so HA reloads
   when the generated content changes
4. A `nix run .#water-attribution-check` flake app that validates the
   generated YAML and verifies every zone slug matches a live HA entity

### What it gives for free

* Type-checked zone definitions (missing `slug` or `name` → build failure)
* Single pass over zones list covers gated template, integration sensor,
  per-zone utility_meter cycles, and the aggregate-irrigation sum-template
* Reproducible YAML via `git diff` on the module
* Pre-activation validation against the live HA entity registry catches
  typos before HA ever sees the file

## Utility meters & period totals (§3)

Every monotonically-increasing total gets daily/weekly/monthly wrappers:

| Source | Category | Count |
|---|---|---|
| `sensor.water_pool_autofill_total` | autofill | 1 |
| `sensor.water_<zone>_total` (×10) | per-zone irrigation | 10 |
| `sensor.water_irrigation_total` | aggregate irrigation | 1 |
| `sensor.water_domestic_hot_total` | hot-water | 1 |
| `sensor.water_other_total` | other | 1 |

Total: **14 cumulative sources × 3 cycles = 42 utility_meter entities**,
generated mechanically.

### Cycle anchors

* `daily` — local midnight reset
* `weekly` — Monday 00:00 local (configurable via `weekStart`)
* `monthly` — 1st of month at 00:00 local

### Aggregate irrigation drop tolerance

`sensor.water_irrigation_total` is a template sum that can dip if a single
per-zone sensor temporarily reports stale state during HA restart. Without
tolerance, HA's LTS would misinterpret that dip as a counter reset.

```yaml
state: >
  {% set s = zones | map('states') | map('float', 0) | sum %}
  {% set last = states('sensor.water_irrigation_total') | float(0) %}
  {% set tol = 5.0 %}   {# Nix-option aggregateDropToleranceGal #}
  {{ [s, last] | max | round(3) if (last - s) < tol else s | round(3) }}
```

Holds at previous value if new sum dips by less than `tol` gallons
(transient); lets actual resets through.

### InfluxDB / VictoriaMetrics tag conventions

Every category entity carries these attributes (become VM tags):

```
water_category   = "autofill" | "irrigation" | "domestic_hot" | "other"
zone_slug        = "<slug>"                 (irrigation entities only)
zone_type        = "spray" | "drip" | null  (irrigation entities only)
generation       = "water_attribution_v1"
```

Grafana queries:

```sql
SELECT sum("value") FROM "gal"
 WHERE "water_category" = 'irrigation' AND "zone_type" = 'spray'
   AND time > now() - 7d GROUP BY "zone_slug"
```

### HA Energy Dashboard

With `device_class: water`, `unit_of_measurement: gal`, and
`state_class: total_increasing`, the four headline cumulative sensors
(`pool_autofill_total`, `irrigation_total`, `domestic_hot_total`,
`other_total`) can be added to Settings → Dashboards → Energy → Water
consumption for stacked daily/weekly/monthly rendering. Post-install step
documented in `WATER_ATTRIBUTION.md`.

## Phase 2 — Weekly cross-check + report (§4)

### Goal

Each week, an independent agent re-derives totals from sources HA didn't use,
and reports any meaningful disagreement plus a friendly summary of the week.

### Sources combined

| Source | Role |
|---|---|
| Flume API | Independent ground truth (direct from device, not via HA) |
| VictoriaMetrics | What HA *thought* the GPM was (catches "HA missed Flume's correct number") |
| HA Postgres `states` | Sub-minute valve open/close events for irrigation attribution |

### Output artifacts (per run)

1. **`sensor.water_attribution_cross_check_delta_gal`** — max abs delta
   across categories, written into HA so dashboards/automations can react
2. **`/var/lib/flume-autofill/reports/YYYY-MM-DD.json`** — structured JSON
   report; format in §4.4 of source design notes
3. **Weekly water report email** — always sent, Mon ~03:30 local
4. **Anomaly section appended to email** — when max delta exceeds tolerance

### Email layout

Plain-text-with-monospace-box format (HTML alternate part included for
clients that render `<pre>` nicely):

```

    Pool autofill             287 gal       198 gal   +45% ⚠
    Irrigation (total)      3,610 gal     3,512 gal    +3%
    Other (cold+misc)       1,449 gal     1,370 gal    +6%
    Total at meter          6,238 gal     5,890 gal    +6%

    Mon 05-15   612 gal    [autofill:42 hot:128 irrig:402 other:40]
    ... etc ...

    • Pool autofill +45% week-over-week.
```

When delta > tolerance, an additional anomaly section is appended with the
hypothesized cause and a `systemctl start flume-autofill-backfill@DATE`
recipe to re-ingest the missed window.

### NixOS wiring

```nix
services.flume-autofill = {
  enable = true;
  weeklySchedule = "Mon 03:30:00";
  deltaToleranceGal = 5.0;
  deltaTolerancePct = 3.0;
  emailTo = "johnw@newartisans.com";
  reportFromAddress = "vulcan@vulcan.newartisans.com";
};
```

Service runs as a dedicated `flume-autofill` system user. Credentials via
`LoadCredential` (never read directly from `/run/secrets/`). Hardened
sandbox (`ProtectSystem=strict`, `ProtectHome=true`, `NoNewPrivileges=true`,
constrained `ReadWritePaths`).

### Rate-limit handling

Flume Personal API: 120 req/hr. A typical 7-day cross-check uses 3-5
requests (single bucketed query returns thousands of points). Script
implements bearer-token caching to `/var/lib/flume-autofill/token.json`
(mode 0600), exponential backoff on 429, and refuses to run more than once
per hour via a `/var/lib/flume-autofill/.run.lock` lockfile.

## Phase 3 — Multi-source backfill (§5)

### Source priority

| Priority | Source | Coverage |
|---|---|---|
| **1** | VictoriaMetrics (127.0.0.1:8428) | Since HA's InfluxDB integration was enabled — deepest local source, 100y retention |
| **2** | Flume Personal API | Since Flume device install — may predate VM |
| **3** | HA Postgres `states` | Bounded by `purge_keep_days` — recent only, but highest fidelity for valve events |
| **4** | HA Postgres `statistics` | Hourly aggregates, coarse fallback |

The backfill tool auto-discovers overlap and reports:

```
Earliest data available:
  VictoriaMetrics    2024-08-12 (sensor.flume_sensor_sierra_oaks_current)
  Flume API          2023-06-04 (device install)
  HA Postgres        2026-05-12 (within purge_keep_days)
  HA Statistics      2024-08-12 (since state_class added)

Will reconstruct from 2023-06-04 (Flume API) and use VictoriaMetrics
for valve-open events from 2024-08-12 onward. Pre-2024-08-12 cannot
attribute irrigation per-zone (B-Hyve integration didn't exist) — those
periods will be tagged 'irrigation_unknown' and counted in the residual.
```

### Destinations

| Destination | Content | Why |
|---|---|---|
| CSV (`/var/lib/flume-autofill/backfill/`) | One file per category, per-day rows | Ground truth; user-inspectable |
| VictoriaMetrics (InfluxDB line protocol) | Cumulative gallons time series, tagged | Grafana renders historical |
| HA Long-Term Statistics | Hourly aggregated per cumulative sensor | HA Energy dashboard shows history |
| Phase 3 report email (optional, `--email`) | Summary of backfilled period | User confirmation |

### Idempotency

Re-running over an already-imported window is a no-op:

* **VM**: (entity_id, timestamp) is the dedup key; same point overwrites
* **LTS**: re-import same hour replaces value. Namespace
  `flume_autofill:water_*` keeps backfilled stats distinct from live
  `sensor.water_*` LTS during development; `recorder.adjust_sum_statistics`
  splices the two at handoff time

### CLI surface

```bash
# Discover what's available
flume-autofill backfill --discover

# Dry run — produces CSV only
flume-autofill backfill --from 2024-01-01 --to 2024-12-31 --dry-run

# Full backfill, all destinations
sudo systemctl start flume-autofill-backfill@2024.service

# Targeted re-ingest of a gap from a Phase 2 anomaly email
sudo systemctl start flume-autofill-backfill@2026-05-18.service
```

The `@instance` systemd template parses `YYYY`, `YYYY-MM`, `YYYY-MM-DD`,
or `YYYY-MM-DD:YYYY-MM-DD` from the instance name.

### Failure modes

* **Flume rate-limit:** chunks queries into ≤1-day windows, sleeps between
  chunks, surfaces ETA. A 2-year backfill is ~730 requests ≈ 6 hours wall
  clock. Resumable from last-successful-day on Ctrl-C
* **VM write throughput:** batches of 1000 line-protocol points with retry
* **LTS atomicity:** each day is one WebSocket call, all-or-nothing
* **Concurrency:** `/var/lib/flume-autofill/backfill.lock` prevents two
  backfill runs at once. Phase 2 cross-check serializes after any in-flight
  backfill

## Testing & validation (§6)

### Unit tests (Python detection module, shared Phase 2 + 3)

* Pure 4 GPM × 15 min → 1 session, gallons within 1% of 60 gal
* 4 GPM × 9 min then drop to 0 → no session (under 10-min threshold)
* 4 GPM × 9 min, 1 min @ 8 GPM, 5 more min @ 4 GPM → 1 session (blip
  tolerance; mean check passes)
* 4 GPM × 10 min, 1 min @ 25 GPM (hose), 5 min more @ 4 GPM → no session
  (mean exceeds 5)
* Two distinct autofills 30 min apart → 2 sessions, no run-on
* B-Hyve zone open during autofill → both detect (independent counters)
* Spray zone with 18 GPM during open window → attributed to that zone,
  autofill detection unaffected
* Hot water flow co-occurring with autofill → both categories accumulate

### Phase 1 HA YAML validation

`nix run .#water-attribution-check` flake app:

1. Renders package YAML
2. Pipes through `hass --script check_config -c /tmp/...` with stub config
3. Verifies every zone slug matches a `valve.sprinkler_control_<slug>_zone`
   in HA's entity registry (`/var/lib/hass/.storage/core.entity_registry`,
   metadata only via `jq`)
4. Verifies Flume current and NaviLink sensors exist

`nixos-rebuild switch` runs this as part of activation.

### Live validation

* **Synthesized event:** trigger a B-Hyve zone manually; observe
  `sensor.water_<zone>_total` increments by `expected_GPM × duration`
* **Detection latency:** measure how soon `binary_sensor.pool_autofill_active`
  flips on after a real autofill begins (expect within 9-10 min)
* **Pre-vs-post-NaviLink:** run a hot tap during a known autofill; both
  `domestic_hot` and `pool_autofill_total` should tick independently

### Phase 2 validation

* First weekly email should show all categories within tolerance
* Per-zone sub-table matches B-Hyve durations × nominal GPM-per-zone
* Intentional HA restart mid-week produces a documented anomaly the
  following Monday

### Phase 3 validation

* Grafana shows continuous data from backfill window through "now" (no gap)
* HA Energy dashboard shows historical bars
* `sensor.water_pool_autofill_monthly` "last month" matches backfill's
  monthly sum within 0.1 gal

### Acceptance criteria

The feature is complete when:

1. `nixos-rebuild switch` deploys the package file, systemd units, and SOPS
   secrets — zero hand-editing required
2. HA has the new categories visible in States view and Energy dashboard
3. Grafana `water-attribution` dashboard shows per-category and per-zone
   time series for the past 30 days
4. First weekly email arrives the Monday after deployment with at least one
   day of data
5. `flume-autofill backfill --discover` reports the multi-source coverage
6. `flume-autofill backfill --from <earliest> --dry-run` produces CSV with
   non-zero values per category
7. Python detection module passes all unit tests
8. A simulated HA restart mid-autofill produces a Phase 2 anomaly the
   following Monday

## Operational concerns (§7)

### Restart & outage behavior

| Component | Effect | Recovery |
|---|---|---|
| HA full restart | Brief gap; integration sensors hold last value; resume after first state change | Phase 2 catches significant gaps |
| Flume integration outage | All gated GPMs go `unavailable`; integration sensors hold last value | Auto-resume; Phase 2 anomaly if outage was long |
| NaviLink outage | `water_domestic_hot_gpm` = 0; that period's hot water shifts into `other` | Auto-resume; mild residual inflation during outage |
| B-Hyve outage | Per-zone gated GPMs = 0 during the outage; flow shifts into `other` | Auto-resume; documented behavior per user choice |
| VictoriaMetrics outage | Live HA data continues; Phase 2 falls back to HA Postgres for comparison | Catch-up on VM return |
| Cross-check service failure | Anomaly email never sent; systemd marks failed; Nagios picks up via existing systemd-check probe | Manual investigation; restart timer |

### Schema evolution

Every entity carries `generation: water_attribution_v1`. Breaking changes bump
to `v2`. Grafana filters on latest generation; historical series remain
queryable at their respective generation.

### Hooks for future Node-RED consumers

The design exposes everything NR would need:

* `binary_sensor.pool_autofill_active` — start/end transition triggers
* `binary_sensor.irrigation_active` — convenience entity (template OR over
  all `valve.sprinkler_control_*_zone` open states)
* `sensor.water_pool_autofill_daily` / `_weekly` — threshold alerts
* `sensor.water_other_daily` — leak-suspicion alerts
* `sensor.water_attribution_cross_check_delta_gal` — pipe to Discord/Hermes

No design change needed to add NR consumers later.

### Documentation deliverables

1. `/etc/nixos/docs/WATER_ATTRIBUTION.md` — user guide
2. `/etc/nixos/scripts/flume-autofill/README.md` — developer guide
3. `/etc/nixos/modules/monitoring/grafana-dashboards/water-attribution.json`
   — Grafana dashboard auto-provisioned via existing mechanism

### Out of scope for v1

* Cold-water indoor flow sensor (would split `other` further if installed)
* Per-zone water cost in dollars
* ML-based "session signature" detection for fully attributing `other`
* Mobile push notifications

## Risks & known limitations

1. **NaviLink covers hot-water only.** Cold-only indoor flow (toilets, cold
   taps, washing-machine cold cycles, ice maker) falls into `other` mixed
   with outdoor non-irrigation/non-pool. Documented in §6.4 above.

2. **Aggregate irrigation drop tolerance is a heuristic.** The 5-gal default
   absorbs transient dips but could mask a real reset if a single zone
   loses ~5 gal of accumulated state. Tunable via Nix option.

3. **Pattern detection has a 9-10 min latency.** The detector cannot decide
   "this is an autofill" until 9 of the last 10 minutes have accumulated.
   Short autofills (e.g., 8-min one-off triggered by float bouncing) won't
   be detected. Per the user choice — false-negative is preferred to
   false-positive.

4. **Flume API depth is the device install date.** If the user has Flume
   data deeper than the API exposes (e.g., from a previous account that
   was migrated), backfill cannot reach it.

5. **HA recorder retention bounds the cross-check.** Phase 2 needs minute
   resolution for the past 7 days, which requires `purge_keep_days >= 7`.
   The existing config satisfies this.

6. **VictoriaMetrics scrape interval defaults.** HA pushes every 60s per
   the existing config; this matches Flume's poll cadence so no resolution
   mismatch.
